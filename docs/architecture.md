# Architecture

The tool monitors a Google Pub/Sub instance — typically the local
`google/cloud-sdk:emulators` mock — by acting as a **transparent gRPC interception
proxy** in front of it. The application under test points `PUBSUB_EMULATOR_HOST` at the
proxy; the proxy forwards every call faithfully to the real server and observes the
traffic on the way through.

It is split into a **headless monitor service** and a **terminal UI**, which talk over
a gRPC stream. The monitor can run wherever the Pub/Sub instance runs (e.g. inside a
`docker-compose` stack); the UI runs on your own machine and connects in.

```
                       ┌─────────────────────── pub-sub-monitor (headless) ──────────────────────┐
app under test ──gRPC──▶ [ proxy ] ──gRPC──▶ Pub/Sub emulator                                     │
                       │     │ observes (taps)        ▲                                           │
                       │     │                         │ 1s admin poll (google-cloud-pubsub)      │
                       │     └── observation events ───┘                                          │
                       │            │                                                             │
                       │   mpsc ──▶ [ state task (single owner) ] ──▶ watch ──▶ [ state server ] ─┼─┐
                       └─────────────────────────────────────────────────────────────────────────┘ │
                                                                                  monitor.v1 gRPC    │ stream
                                                                                                     ▼
                       watch ◀── [ state client ] ◀───────────────────────────────── pub-sub-tui ───┘
                         │                                                            (ratatui, on host)
                         └──▶ [ ratatui render loop ]
```

The split is along the existing `watch`-channel seam: where the UI used to read
snapshots from an in-process `watch` channel, it now reads them from a local `watch`
channel fed by the gRPC client. The render loop is unchanged.

## Why a proxy

Pub/Sub's metadata/admin API exposes topics and subscriptions, but it has **no concept
of publishers** and exposes **no message counts** (those live only in Cloud Monitoring,
which the emulator does not implement). The traffic itself, however, contains all of it.
By forwarding the traffic we can observe — with real data — exactly what the README
describes, without changing the behaviour of the application under test:

| Feature (README) | Source |
| --- | --- |
| Running count of topics | 1s admin poll (`google-cloud-pubsub`) |
| Tree of topics with non-zero message counts | observed `Publish` traffic |
| Publishers on a topic + per-publisher counts | observed `Publish`, keyed by client peer address |
| Consumers on a topic + consumed counts | observed `Pull`/`StreamingPull` + `Acknowledge` |
| Total publishers/consumers connected | active publishers (recent window) / live `StreamingPull` connections |
| Real-time, or a one-second polling tick | live traffic stream / admin poll |
| Borland colour scheme, resize, `LOG_LEVEL` | the TUI itself |
| Only reads metadata; apps unaffected | the proxy forwards every call verbatim |

"Only reads metadata" is honoured in spirit: the proxy is a read-only observer that
relays requests and responses (and any error `Status`) unchanged, so a client behaves
exactly as if it had talked to the server directly.

## Components

- **`proxy`** (`src/proxy/`) — a tonic server implementing the `Publisher` and
  `Subscriber` services. Every RPC is forwarded to an upstream client over a single
  lazily-connected channel. Pure pass-through methods are generated by the
  `proxy_service!` macro; the tapped ones are hand-written:
  - `Publish` → counts messages per topic, attributed to the client peer address.
  - `Pull` / `Acknowledge` → delivered / consumed (acked) counts per subscription.
  - `StreamingPull` (bidirectional) → actively pumped in both directions with
    `tokio::select!`, latching the subscription from the first frame, counting acks and
    deliveries, and opening/closing the live consumer when either direction ends. The
    active pump (rather than a passive forward) is required both to avoid an
    establish-before-feed deadlock and to detect a disconnect on an otherwise-idle stream.
- **`poller`** (`src/poller.rs`) — uses the `google-cloud-pubsub` crate to list topics
  and subscriptions every second, emitting an admin snapshot. It connects **directly to
  the upstream** (via `Environment::Emulator`), never through the proxy, so polling does
  not loop back or pollute traffic metrics, and it also catches entities created
  out-of-band.
- **`observe`** (`src/observe/`) — the single state owner. Proxy handlers and the poller
  send cheap `Observation` values down an mpsc channel (never blocking the data path);
  one task folds them into `AppState` and publishes immutable snapshots over a `watch`
  channel. This keeps the hot path lock-free and gives the UI an always-latest view.
- **`monitor`** (`src/monitor/`) — the network boundary between the headless service and
  the UI, implementing the `monitor.v1.Monitor` gRPC service:
  - `server` wraps the observer's `watch` receiver in a `WatchStream` and serves it as a
    server-streaming RPC, so every connected UI gets the current snapshot immediately
    and a fresh one on every change. It is a pure fan-out tap and owns no state.
  - `client` (UI side) dials the monitor, pumps the snapshot stream into a local `watch`
    channel, and reconnects with backoff if the connection drops — so the UI starts
    cleanly even before the monitor exists.
  - `convert` mirrors `AppState` to and from the wire types. Publisher liveness is held
    in-process as an `Instant`, which is meaningless off-host, so it is sent as
    *milliseconds since last seen* and rebuilt against the UI's own clock on receipt;
    the recent-activity window then keeps working with only the sub-second stream
    latency as skew.
- **`ui`** (`src/ui/`) — ratatui + crossterm. A dedicated thread reads input events; the
  render loop selects over input, a one-second tick, and state-snapshot changes. The
  terminal is restored on exit and on panic (via the hook installed by `ratatui::init`).
  The topic tree (`src/ui/tree.rs`) builds a trie from each topic id's dotted segments,
  so related topics nest under shared group nodes that can be drilled into.
- **`loadgen`** (`src/loadgen.rs`) — a demo traffic generator. It creates a tree of
  hierarchically-named topics, attaches subscriptions to most of them, and continuously
  publishes and (via streaming pulls) consumes — all through the proxy, using the raw
  generated gRPC clients, so the monitor observes the full range of activity.

## Binaries

All three are thin shells over the library (`src/bin/`):

- **`pub-sub-monitor`** — the headless service: starts the observer, the poller, the
  proxy and the state server. Logs to stderr.
- **`pub-sub-tui`** — the UI: streams state from a monitor and renders it. Logs to a
  file (it owns the terminal).
- **`pub-sub-loadgen`** — drives `loadgen` against a proxy endpoint. Logs to stderr.

## Identity and liveness

- A **publisher** is identified by its client peer address (`ip:port`). Because `Publish`
  is a unary call with no long-lived connection, a publisher is counted as "connected"
  if it has published within a recent window (10s).
- A **consumer** is a `StreamingPull` connection (or an individual `Pull`/`Acknowledge`
  caller); live consumers are the currently-open streaming connections.

## Known limitations

- Publisher identity collapses connections that a client multiplexes onto a single
  socket into one peer.
- The "connected publishers" figure is a recent-activity window, not a live socket count.
- These reflect what Pub/Sub traffic can actually reveal; they are not arbitrary.
